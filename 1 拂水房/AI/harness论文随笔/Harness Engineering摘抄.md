## 一句话总结
Harness Engineering = 工程师不再写代码，而是**设计环境、明确意图、构建反馈回路**，让 AI 智能体可靠地完成工作。
## 人类掌舵，智能体执行（Humans Steer, Agents Execute）
- 人类时间是最稀缺的资源
- 出问题时，答案不是"更努力"，而是"缺什么上下文/工具/约束"
- 工程师的新角色：设计环境 → 拆解任务 → 提示智能体 → 验证结果
##  吞吐量改变合并理念
当 Codex 的吞吐量远超人类注意力时，传统的工程规范变得不再有效。
核心转变：**纠错成本低，等待成本高。**
- ❌ 每次改动跑全量测试
- ✅ 优化迭代速度，快速发现和修复问题
- ✅ 便宜模型（Sonnet/Haiku）做子任务，贵模型（Opus）做编排
### LangChain — Ralph Loop 机制

长时间自主执行需要：

1. 文件系统 + git 追踪持久化工作
2. **Ralph Loop** 拦截退出，在新上下文窗口中重注入原始提示词
3. 规划 + 自我验证分解目标为步骤
### 关键洞察
```
传统模式：人力贵 + 吞吐量低 → 每个 PR 都要精心审查 → 阻塞门多
Harness 模式：智能体便宜 + 吞吐量高 → 快速迭代修复 → 阻塞门少
```

前提条件：必须有足够的**背压机制**（测试、lint、结构检查）来保证基本质量，否则就不是"快速迭代"而是"快速腐烂"。
# Agent = Model + Harness
## 常见模型问题
### 常见AI困境
- 上下文腐烂（Context Rot）：上下文窗口被日志、工具输出填满，模型逐渐"忘记"原始指令；
- 工具调用幻觉（Hallucinated Tool Calls）：调用一个根本不存在的 API，或传错参数类型，没有校验就陷入无限失败循环；
- 失败时状态丢失（Lost State）：网络一超时、服务一重启，进度清零；
- 过早停止（Early Stopping）：任务没干完，模型就宣称成功；
- 成本失控：反复调用昂贵 API，账单失控。
### 工程范式的三次跃迁
- 2022–2024：提示工程（Prompt Engineering）——优化单次模型调用的输入；
- 2025：上下文工程（Context Engineering）——重心转向"每一步该给模型什么上下文"；
- 2026：Harness 工程（Harness Engineering）——可靠性越来越依赖模型外层的基础设施：状态管理、工具协调、反馈注入、约束施加、进展验证。
### 实际落地的难点与痛点
1. 上下文腐烂（Context Rot）。长任务上下文窗口必然被填满，模型"忘记"目标。需要压缩 / 摘要 / 工具输出卸载（只保留头部尾部，完整内容落盘按需检索）。
2. 工具调用幻觉。模型调用不存在的 API、传错参数类型。必须靠严格的 schema 校验、参数验证、tool 注册表兜底，否则会无限失败循环。
3. 状态丢失与不可恢复。网络超时、服务重启就让进度清零。需要 checkpoint、持久化、resumable execution。Anthropic 特别强调：长任务必须有"可恢复的执行基础设施"和"清晰的交接产物"。
4. 过早停止。模型任务没完成就报成功。需要自验证、rubric 红笔批改、测试门禁来兜底。
5. 成本失控。Agent 反复调用昂贵 API，账单爆炸。需要步数 / 预算上限、资源限制（CPU、内存、时间）。
6. 安全与沙箱。让 Agent 生成的代码在本地直接执行极危险。需要 Docker / E2B / Landlock 等沙箱、命令白名单、网络隔离。DeepAgents 明确"信任模型，但边界放在工具 / 沙箱层"；DSH 内置基于 Linux Landlock 的原生沙箱。
7. 可观测性与调试黑洞。长链路失败极难定位，只能看到最终结果。需要轨迹、成本、失败与可靠性信号的全程采集——这正是 DSH 把"轨迹"作为一等公民的原因。
8. 评测难题。同一模型，在不同 harness 里表现可能差异巨大——harness 本身成了 benchmark 的变量。需要可重置、可复现的环境，并结合单步、完整回合、多轮评测。LangChain 的经验是：评测与可观测性不应割裂，而应视为同一个反馈回路。
9. 自进化与治理的两难。DSH 的"运行时自挂载插件"引发争议：开发者宝玉（@dotey）质疑"软件自进化"可能是伪命题——软件需要严谨设计与验证，过度自动化反而导致混乱。这恰恰凸显了 ETCLOVG 里"治理层"的必要性：权限、身份、策略、审计、人工监督一个都不能少。
10. Demo 到生产的鸿沟。跑通一个 demo 很容易，但生产需要权限体系、审计、多租户、SLA 与可恢复性。很多团队卡在这一步。
11. 多模型兼容与生态碎片化。DSH 对非 DeepSeek 模型仍存在兼容摩擦；插件生态虽爆发（发布数日 700+ 个 dsh-plugin），但质量良莠不齐，存在插件间"攻防"（如广告插件 vs 去广告插件）。
### 几点落地的经验
- 先分清 framework 还是 harness，别重复造轮子——多数业务用现成 harness 就够了；
- 安全边界放在工具 / 沙箱层，不要指望模型自律（"trust the LLM"，但约束在工具侧）；
- 上下文渐进式提供，别一次性把全部信息倒给模型（Anthropic 的实战经验）；
- 把可观测性和评测当成同一个反馈回路，而不是两套割裂系统；
- 长任务必须有 checkpoint 与清晰交接产物，否则一次中断就前功尽弃；
- 先用成熟方案验证业务价值（DeepAgents / Claude Code），再考虑用 DSH 这类可重写底座做深度二次开发。
