## 一、什么是 Agent Skill？

**Skill = (Function + Metadata + Trigger Logic)**

- **Function**：实际执行逻辑（如 Python 函数、API 调用）
- **Metadata**：描述该技能的名称、描述、输入/输出格式、参数说明（供 LLM 理解）
- **Trigger Logic**：何时被调用（由 Planner 或 Router 决定）

```
# 技能：查询当前天气
```

是不是有种似曾相识的感觉？没错——这不就是 **Tools（工具）** 吗？

从本质上讲，**Skills（技能）和 Tools 其实是一回事**：它们都是 Agent 用来完成特定任务的能力模块。但在实际构建 Agent 的过程中，两者在使用方式上却存在关键差异。

传统的做法是，在 Agent 初始化时就将所有可能用到的 Tools 及其详细描述一股脑注入上下文。这种“全量预加载”的方式看似方便，实则隐患重重：

- 一旦 Tools 数量庞大，极易导致上下文长度爆炸；
- 模型不仅要处理任务本身，还要在海量工具信息中“大海捞针”，造成严重的 **信息过载**；  
    
- 不仅浪费计算资源，还可能影响推理准确性和响应速度。

为了解决这一痛点，**Skills 的概念应运而生**。  
与传统 Tools 不同，Skills 采用 **按需加载（on-demand loading）** 的策略：

1. **先加载轻量级的工具说明（metadata）**，用于判断当前任务需要调用哪些能力；
2. **仅在确定所需工具后，才动态注入对应的完整工具定义和参数**，再执行调用。

这种方式不仅显著降低了上下文负担，还提升了 Agent 的响应效率与可扩展性——尤其在面对复杂、多工具协同的场景时，优势尤为明显。

简言之：**Tools 是“全副武装上战场”，而 Skills 是“按需配装打胜仗”**。

## 二、Skill 设计原则

在构建 Agent 的能力模块时，**Skill 不只是功能的封装，更是智能体可靠性和可扩展性的基石**。基于我们在多个 Agent 项目中的实践与反思，一个高质量的 Skill 应严格遵循以下五大设计原则：

|原则|说明|
|---|---|
|原子性|每个 Skill 只完成单一、明确的任务。例如，“发送邮件”是一个合格的 Skill，而“处理用户请求并发邮件”则应拆分为多个 Skill。原子性确保了复用性与组合灵活性。|
|无状态|Skill 的执行结果仅由输入参数决定，不依赖外部环境或历史上下文。所有状态应由 Agent Manager 或对话控制器统一维护，避免隐式依赖导致的不可预测行为。|
|可描述|必须提供清晰、简洁的自然语言描述（包括功能、输入格式、适用场景等），让 LLM 能准确判断“何时调用、如何调用”。这是 LLM 有效调度 Skill 的关键前提。|
|可测试|支持确定性单元测试：给定固定输入，应能稳定输出预期结果。这不仅便于调试，也为自动化验证和持续集成提供基础。|
|安全可控|所有 Skill 都应遵循最小权限原则。例如，禁止直接执行高危操作（如删除文件、修改系统配置）；敏感操作需通过沙箱隔离、人工审批或权限校验机制加以控制，防止滥用或误用。|

💡 小结：好的 Skill，不是“能跑就行”，而是可理解、可组合、可信赖的原子能力单元。它既是 Agent 的“手脚”，也是系统安全与稳定的第一道防线。

但理想很丰满，落地仍需打磨。在真实业务场景中，我们常常面临这些关键挑战：

- 如何对**敏感操作**（如资金转账、用户数据删除）进行有效拦截或触发**人工二次确认**？
- 如何在保持 Skill 调用灵活性的同时，落实**最小权限原则**，并确保所有操作**可审计、可追溯**？
- 面对多变、复杂的业务流程，如何动态调整 Skill 的**调用策略、参数组合**甚至**失败重试机制**？

这些问题没有放之四海皆准的答案——**通用框架只能提供骨架，血肉必须由具体业务来填充**。唯有深入场景，在**安全性、执行效率与用户体验**之间反复权衡，才能构建出真正可用、可信、可持续演进的智能 Agent。
